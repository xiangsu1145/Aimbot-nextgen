## 1. 触摸融合为什么不生效

### 1.1 三个定义互相矛盾（先要定语义）

- `input/uinput_inject.h:133-146`：fusion = **takeover**，aim 驱动物理手指，单触点。
- `ui/gui/sections/aim_section.h:275-281`：fusion ON = 合成手指 + delta 叠加；OFF = takeover。
- `aim_section.cpp:1011 / 1035-1043`：按上面第二种实现。

`uinput_inject.h` 是 09-15，`aim_section.cpp` 是 09-19。后改的是 aim 侧，头文件注释没同步。**所以先确认你要的是哪一种**（见 §5 决策点）。

### 1.2 直接原因（按影响排序）

**(a) 融合的锚点错了 —— 这是"看不到融合触点"的主因** `aim_section.cpp:1037-1043`

fusion ON 时走 `p.touchAim.press(p.touchArea)`，合成手指落在**触摸框中心 ± jitter**（`aim_section.cpp:579-580`），与玩家的物理手指位置**无关**。玩家手指在框内某处，自瞄手指从框中心出发追目标 —— 游戏里就是两个各自独立运动的触点。

真融合应当让触点**锚定在物理手指上**（`position = 物理手指位置`），再叠加 aim 增量；或者直接接管（takeover）。当前两者都不是。

**(b) `p.touchAim.realId` 在每次进入 Pressed 时被清零** `aim_section.cpp:1039`

delta 的前提是 `p.touchAim.realId == realId && lastPhysX >= 0`（`:996`）。press 那帧把 `realId` 置 -1，下一次 delta 必为 0；每次重新 press（目标丢失、切换目标、drag safety 触发 `:1085`）都要重新同步一次。不是致命，但每次都是 1~2 帧真空中断。

**(c) 取指范围与开火判定不是同一个区域**

- 融合取指：`realFingerInTouchArea()` —— 触摸框内、离框中心最近的（`:199-221`）
- 开火判定：`realFingerInTriggerArea()` —— 触发区圆内（`:874 / :180-193`）

玩家用来开火的手指在触发区，但它**不一定在触摸框内**。一旦不在，`realFingerInArea` 恒 false、`physDelta` 恒 0，**融合静默失效，没有任何日志**。

**(d) delta 被两处逻辑吃掉** `driveAimToTarget` `:253 / :263-283`

- `if (xInDz && (yInDz || yInYFollow)) return;` —— 死区命中时整帧早退，物理 delta 不消费
- `dot <= 0` 时物理 delta 整帧丢弃；只有方向一致才叠加

玩家侧感受就是"手指在拖，屏幕几乎不动"。

**(e) 遗留死代码** `TouchAimState::physX/physY` 从未被写入（只在 `release()` 归零），`justReleasedTakeover` 在 fusion ON 下永不置位 —— 说明这块重构过但没清理。

### 1.3 建议改法

给融合加一个三态（或至少翻转现有 ON/OFF 语义），全部复用现有 uinput API：

| 模式 | 实现 | 屏幕触点 | 适用 |
|------|------|----------|------|
| 合成 | `uinput_down(UINPUT_SLOT_PRIMARY)` + `uinput_move` | 1 个（独立的） | 无物理手指时兜底 |
| 锚定混合 | 合成手指 press 在**物理手指位置**，aim 增量 + 物理 delta 叠加 | 2 个几乎重合 | 保留玩家微调 |
| 接管 takeover | `uinput_takeover_physical_id` + `uinput_move` + `uinput_release_takeover` | **1 个，就是玩家的手指** | 最自然，推荐默认 |

takeover 路径**已经完整实现**（`uinput_inject.cpp:1005-1046` 及 mirror 的槽位排除 `:1271-1274 / :1301 / :1311`），现在只是挂在 fusion OFF 上。

最小改动版：把 `:1011` 的条件从 `!p.fusion.value` 翻成 `p.fusion.value`，同时把 `:994` 的 delta 分支条件翻转，注释同步修正到 `uinput_inject.h` 的语义。这就能让"融合"变成单触点接管。

## 2. 丢框之后目前怎么补偿的

存在两层，缺一不可：

**tracker 层** `kalman_tracker.cpp:175-203 (predictAll)`
- lost 后 `predictHoldFrames`（默认 3，Aim 页滑条 "trackPredictHoldFrames"）内：用常速模型 `x = A*x` 继续沿 (vx, vy) 外推
- 超过该窗口：`t.x = t.last_valid` 且 vx/vy 置 0 —— **冻结在最后有效位置**
- `terminateFrames`（默认 5，Settings 页）后 track 被删除，id 归还 `freeIds_`

**aim 层** `aim_section.cpp:921-940 / 1047-1058`
- `tracks()` 输出**包含 lost 的 track**（只过滤 `!confirmed`），所以丢失期间 `hasTarget` 仍为 true，手指继续朝冻结/外推位置推
- 直到 track 被删那一帧 `hasTarget=false`，才 `uinput_up` / `uinput_release_takeover`

### 缺陷

1. **`update()` 在 `dets.empty()` 时不调用 `predictAll()`** `kalman_tracker.cpp:339-345`
   → 整帧无检测时 `lost_frames` 不递增、不沿速度外推，实际表现为"立即冻结"；但 `terminate_count` 照常在 `matchAndUpdate` 里递减。
   → 于是"模型整帧空输出"和"部分目标丢失"两套补偿行为不一致（前者立即冻结，后者先外推 3 帧再冻结）。
   → 修法：`dets.empty()` 分支也调用 `predictAll()`，再走 `matchAndUpdate`。

2. **lost 目标没有衰减约束**：`score` 沿用最后一次匹配的值（`:271`），丢失目标可以在墙后越推越远却仍被高优先级瞄准。建议对 lost 目标按丢失帧数线性衰减 `score`，或在 aim 侧对 `t.lost` 的候选加距离惩罚。

3. **`aimDelayFrames` 对 lost 目标照常生效** `aim_section.cpp:948-951`：继续用旧速度外推，会越推越偏。建议 lost 目标的前导量按 `lost_frames` 折减。

## 3. 选靶：从"最近"改为"持续追踪"

现状 `aim_section.cpp:922-940`：每帧遍历全部 confirmed + 类别命中的 track，取 `dSq` 最小者。新目标更近就立刻换靶 —— 瞄准点瞬移、视野抖动、id 无意义。

### 设计：粘性目标锁

`PageAim` 新增：

```cpp
int  lockedId  = -1;      // 当前锁定的 track id（-1 = 未锁定）
int  lockedAge = 0;       // 已连续锁定帧数（可观测/调试用）
widgets::SwitchState sticky{true};              // 粘性追踪总开关
widgets::SliderState switchMargin{0.0f,0,1,0.05};  // 切换门槛：新目标须近 X% 才换
widgets::SliderState lockLostFrames{6.0f,0,30,1};  // 目标 lost 后仍保持锁定 N 帧
widgets::SliderState lockMaxDist{0,0,2000,10};     // 锁定目标离准心超 X px 才放弃
```

每帧选择逻辑（替换 `:921-940`）：

1. 构造候选集：`confirmed && isClassSelected(t.cls)`
2. `lockedId >= 0` 时按 id 在候选集里找：
   - **找到 → 直接用它**，不比较距离（含 `t.lost`，因为 tracker 自身有 hold 窗口）
   - 找到但 `t.lost` 且 `lockedAge` 超过 `lockLostFrames` → 解锁
   - 没找到（track 已被 terminate，id 已归还）→ 解锁
3. 解锁后重选：仍按"距准心最近"，并把新 id 写回 `lockedId`
4. **可选迟滞**（防抖）：锁定期间若存在候选且 `d_new * (1 + switchMargin) < d_locked`，允许换靶。`switchMargin = 0` 即"永不主动换靶"

配套：
- 类别勾选变化导致锁定目标类别被取消 → 立即解锁（第 2 步的候选集判定天然覆盖）
- `tracker().reset()` 时（`snap.active == false`，`:844`）把 `lockedId` 一起置 -1
- HUD 上给锁定目标画不同颜色框 + 显示 id，便于验证（`hud.cpp:750`）

## 4. 关联算法：能用匈牙利，但要先修代价函数

### 4.1 现状

`kalman_tracker.cpp:205-301 matchAndUpdate`：**按类别分组 + 组内贪婪 best-IoU**，阈值 `iouThreshold = 0.5`（严格大于）。

### 4.2 直接回答：能，而且和"持续追踪"是配套的

匈牙利（Kuhn-Munkres / 简化 Jonker-Volgenant）给出**全局最小代价**匹配，能消除贪婪的经典失败：两目标靠近或交叉时，贪婪会先用最高 IoU 配对，导致第二条边被迫选择次优解，表现为两个 id 互换。

但要说清楚优先级：

- **瓶颈是代价函数，不是求解器。** 现在代价只有 IoU：目标快速移动或检测帧率低时前后帧框不重叠 → IoU = 0 → 全部配不上 → 每帧新建 track、id 疯狂增长。**这种情况下换匈牙利一点用都没有**（Hungarian 只是在无解里挑最不难看的）。而 id 不稳定，"持续追踪同一个目标"根本无从谈起。
- **类别是硬约束**，应当保持 per-class 分别求解（现在的分组结构可以直接保留）。

### 4.3 建议改法（SORT 标准做法）

1. **代价矩阵用 Kalman 预测框**，不要用上一帧框：
   `C[i][j] = 1 - IoU(track_i.predicted, det_j)`
   （`predictAll()` 已经算出预测位置，取 `t.x` 即可）
2. **加 gating**：中心距离 > `maxGateDist`（建议按框尺寸自适应，如 `1.5 * max(w, h)`）的格点直接禁配，避免把远处的检测错配给快消失的 track
3. **跑匈牙利**求全局最小代价，再丢弃代价超过阈值的配对
4. 剩余检测 → 新建 track；剩余 track → `lost` 计数（现有逻辑不动）

实现成本：项目无 Eigen/OpenCV，需要自己写。n ≤ ~20 时 O(n³) 的实现约 60~100 行纯 C++，可直接放进 `kalman_tracker.cpp` 的匿名 namespace（和现有 `Mat` 放一起）。目标数少，每帧开销可忽略。

**也可以分两步走**：先只做 (1)(2)，实测 id 稳定性若已达标就不必上 (3)。判断标准：锁定目标连续跟踪 10 秒，`lockedId` 不变更次数 = 0。

## 5. 决策点（已确认）

1. **"触摸融合"的语义 → A 的变体，即"接管 + 单向助力"。**
   手指在触摸框内时，**不新接触点**，自瞄直接在**这根手指的坐标上**加增量；
   手指可以往自瞄移动的方向推（正向助力），**不能反向**（反向分量整段丢弃）。
   融合 OFF 则退回纯合成触点，玩家手指原样镜像、自瞄绝不碰它。
   > 与原始 A 的区别：A 是"aim 独占手指"，现在是"aim 与手指共享，但手指只有正向权限"。
2. **换靶策略**：暂缓，等关联稳定后再说（见 §3，尚未实施）。
3. **匈牙利**：暂缓，先修代价函数 + 门控（§4，尚未实施）。

## 8. 为什么"怎么调都跟不上"

PPID 是比例律，且 `smoothTerm` 在实用区间内近似线性，**等效比例增益**为

```
gain = kp * (10000 - smooth) / 10000
     = 25 * (10000 - 9900) / 10000 = 0.25
```

即每帧只走掉剩余误差的 25%。对静止目标这没问题（4 帧时间常数）；但对以 `v` px/帧匀速运动的目标，稳态误差恒为

```
e_steady = v / gain = 4v
```

- 目标 10 px/帧 → 恒定落后 40 px
- 目标 30 px/帧 → 恒定落后 120 px（框已经比目标还宽）

**这个偏差不是调参能消掉的**：`kp` 调大只是把"落后"换成"振荡"，因为环路里还有 2–4 帧的推理+投递延迟。

别人的控制器能跟住快目标，靠的不是更大的 kp，而是**前馈**：把目标自身的速度直接加到手指位移上。自瞄最终控制的是一根手指，手指动多少、画面转多少；只要让手指以目标的速度一起走，稳态误差就归零，反馈项只剩修正残差。

原来间接做了这件事——`延迟补偿 × vx`——但上限只有 **1.0 帧**，而真实延迟链是 2–4 帧，最多只能补回四分之一。

> ⚠️ **本节写于第一轮改动。** 其中的 `smoothTerm` 增益公式、以及"平滑往上调就是降增益"的说法，在第二轮被证明是**旋钮接错了线**（那根滑条根本不是平滑，是一根 5000 倍跨度的反比增益），已重写 —— 见 §9。

## 9. 第二轮：旋钮接错了线（2026-09-20 晚）

四个主观描述 —— "平滑拉小很抖、拉大没作用"、"预测拉大乱抖"、"前馈根本没法跟枪"、"检测框慢半个身位" —— 不是四个问题，是**两个根因**。

### 9.1 根因 A：Kalman 的时间基准错了，位置被反复拉回过期测量

`hud.cpp:847` 在 **120 Hz** 渲染循环里调 `syncAimPage()`，后者无条件调 `tracker().update(snap.detections)`。但检测快照 `g_snapshot.detections` 只在**推理完成时**更新，而推理上限是 `kInferenceFps = 60`。

结果：**同一份 detections 被喂给 tracker 两次**。

CV Kalman 的流程是"用 (vx,vy) 预测下一帧位置 → 向测量修正"。喂重复测量时，第二步会把已经预测出去的位置**拉回一个已经过期一帧的测量上**。用本工程自己的稳态增益（K_pos=0.82、K_vel=0.42）数值模拟，目标每检测帧移动 100 px、渲染 120 Hz：

| | 重复关联（原状） | 只关联新鲜帧（修复后） |
|---|---|---|
| 输出位置滞后 | **9 ~ 41 px 来回跳** | ≈ 0 px |
| vx 估计 | **39 ~ 61（±22% 振铃）** | 49.8（真值 50） |

两个后果，正好对上你描述的现象：

1. **"框慢半个身位"**：位置被持续往回拉，平均滞后约 1/4 检测帧，而且在两个值之间跳 —— 所以框看起来既后面又不稳。这是**烙进目标位置里的滞后**，任何增益都消不掉，因为控制器追的就是这个已经偏后的点。
2. **"前馈开大就是乱抖"**：vx 不收敛，在 ±22% 之间振铃；而 `延迟补偿` 和 `速度前馈` 都是 `vx × 系数`，**vx 的波动就变成手指的抖动**。这解释了为什么单独放大某一项只会更糟。

**修法**：`MultiTracker::update(dets, freshMeasurement)`。

- 渲染帧**始终**推进运动模型 ⇒ vx 单位 = px/**渲染帧**，与手指每渲染帧移动一次的单位一致。这是修复的关键：位置因此能平滑地追着显示走，而不是被反复拽回
- 关联、丢失计数、新建 track **只在新鲜检测帧**执行
- 新鲜度由 `Snapshot::detSeq` 判定 —— 它与 `detections` 在**同一把锁**下自增。用 `ran` 不行：那是 worker 线程计数，会产生"ran 已变、列表未换"的错位，反而漏掉一帧真检测

### 9.2 根因 B：`平滑` 不是平滑，是 5000 倍跨度的反比增益

```cpp
outputScale = bandwidth - smooth                      // bandwidth = 10000
K_p = smoothTerm(kp*error, 10000, 10000 - smooth)
    ≈ kp * error * (10000 - smooth) / 10000           // 实用区间内
```

它从未做过任何平滑，只是把输出乘了个系数。数值核算（`kp = 25`）：

| 平滑 | 等效增益 |
|------|---------|
| 9500 | 1.25 |
| 9700 | 0.75 |
| 9900 | 0.25 ← 出厂默认 |
| 9950 | 0.125 |
| 9999 | 0.0025 |

**500 倍跨度、反比、无中间可用区间。** 这个滑条你只推了一点点（9500→9999，看起来不过 5% 的行程），增益却差了 500 倍：拉小 → 增益 1.25（>1）配合 2–4 帧环路延迟必然振铃；拉大 → 增益 0.0025，于是"其他滑条全都没反应"。**这不是手笨，是旋钮被接成了一根增益线。**

**修法**（`tracking/pid_controller.h`）：

1. `kp/kd` 归一化：`gainP = kp / 50` —— 语义变成"这一帧吃掉剩余误差的比例"，kp=25 就是走一半。可推理、可预期。
2. `smoothTerm()` → `softLimit(v, L) = L * tanh(v / L)`：原点斜率**严格为 1**，只在 |v| 逼近 L 时饱和。它只防离群点（重新锁定时目标瞬移），正常跟踪时完全透明。
3. 滑条改名 **输出限幅**（20–400 px/帧，默认 120）。

### 9.3 附带修复：关联在快目标上必然断裂

`trackIou` 原为 **0.5**。100 px 宽的框以 60 px/检测帧横移时，相邻两帧 IoU ≈ 0.2 —— **每帧都配不上** ⇒ track 每帧被删掉重建 ⇒ 新 track 的 `vx` 初始化为 **0**、位置取原始检测。于是：

- track id 乱跳、框抖
- **vx 恒为 0 —— 任何前馈都等于没开**

这是"前馈根本没法跟枪"的第二重原因（与根因 A 叠加放大）。

**修法**（`matchAndUpdate`）：

- 关联分数 = `IoU + 0.3 × max(0, 1 - 归一化中心距)`，IoU=0 时仍有梯度
- gating：中心距 > `gateRadius(1.5) × 0.5(w+h)` 直接禁配，防止"最近的那个框"跨屏误配
- `trackIou` 默认 0.5 → **0.15**，范围 0.05–0.6

### 9.4 关于"检测框慢半个身位"

你看到的框画的是 `t.cx/t.cy`（`hud.cpp:766`），和自瞄用的是同一个数 —— 所以**框慢 = 目标位置本身就慢**，控制器在追一个已经在后面的点。

慢的构成：检测管线（capture→infer→post）+ Kalman 后验滞后。修完根因 A 后 tracker 每渲染帧推进一次运动模型，滞后只剩检测管线本身，`延迟补偿` 此时才真正补得上它。

### 9.5 四个速度旋钮的分工

| 滑条 | 作用 | 默认 |
|------|------|------|
| `速度前馈` | 补偿**控制器**慢：`move += vx·f`，f=1 时稳态误差归零 | 1.0 |
| `延迟补偿` | 补偿**测量**旧：`target += vx·D`，D ≈ 测量滞后帧数 | 1.0 |
| `预测X/预测Y` | I 通道放大，读的是差分速度（噪声大） | **0**（建议保持） |
| `预测帧数` | 丢框后沿 vx 外推多久（**与跟枪无关**） | 3 |

推导：设有效增益 `g = kp/50`、测量滞后 `τ` 帧、目标速度 `v`，则

```
e_steady = v · (1 - f - g·D) / g  +  τ·v
```

要让稳态偏差归零 ⇒ `f + g·D = 1 + τ·g`。取 `f = 1`、`D = τ` 即为一组正解 —— **前提是 vx 准确**，这正是根因 A 必须先修的原因。

### 9.6 调参顺序（这次是确定的流程）

1. `预测X/Y = 0`、`死区 = 0`、`输出限幅 = 400`、`速度前馈 = 1.0`、`延迟补偿 = 0`
2. 加大 `Kp` 直到准心在目标两侧来回摆 —— 记下这个值 `Kp_crit`
3. 退到 `Kp = 0.4 × Kp_crit`
4. 逐步加 `延迟补偿`（每次 +0.25），到"跟手但不冲过头"为止
5. 微调 `速度前馈`：仍落后 → 1.1~1.3；冲过头 → 0.8~0.9

若第 2 步 `Kp` 加到 50 都还不振铃，说明该游戏灵敏度偏低，可把 `速度前馈` 提到 1.3~1.5 补足。

> ⚠️ **§9.6 的流程已被 §10 取代。** 它的前提（P 律 + 前馈）在第三轮被数值仿真证伪：P 律在延迟环上根本没有可用增益区间，无论怎么调都只能在"振铃"和"滞后"之间跳。

## 10. 第三轮：为什么"怎么调都在两个坏档位之间"（2026-09-20 深夜）

### 10.1 先直接回答：检测框用了预测吗

**没有。** 项目里有两个独立的画框开关，画的是两份完全不同的坐标：

| 开关 | 绘制函数 | 数据来源 | 标签长什么样 |
|---|---|---|---|
| 显示检测框 | `hud.cpp:705` `drawDetectionOverlay()` | `snap.detections` —— **模型原始输出** | `人物 0.87` |
| （跟踪框） | `hud.cpp:750` `drawTrackingOverlay()` | `tracker().tracks()` —— **Kalman 平滑+预测** | `#7` |

所以：

- 看到的是 `名字 + 置信度` ⇒ **原始检测框，没有预测、没有控制器参与**。它稳只证明模型和输入稳。
- 看到的是 `#数字` ⇒ 那是 Kalman 的预测位置，这才是"带预测"的框。

**这个区别是整件事的关键**：原始检测框告诉你"目标在哪"，那是**测量值**；自瞄是**带延迟的闭环**，跟踪的是被延迟污染过的误差。框完美 ≠ 自瞄能跟。你观察到的"框很稳"恰恰把嫌疑全部锁定在**控制器**这一段。

### 10.2 两个坏档位是同一个病的两个剂量

离散 P 律 + L 步传输延迟，稳定上界是

```
Kp < 2 · sin( π / (2·(2L+1)) )
```

| 延迟 L（步） | 稳定上界 |
|---|---|
| 2 | 0.62 |
| 3 | 0.45 |
| 4 | 0.35 |
| 5 | 0.29 |

而 P 律对**匀速**目标有**固有**稳态误差：

```
e_steady = v / (plant_gain · Kp)
```

两式联立就是死局：

- `Kp` 调大到稳定上界附近 → 抑制滞后，但延迟把相位拉开 → **振荡**
- `Kp` 调到远低于上界 → 不振铃，但 `e_steady ∝ 1/Kp` → **恒定滞后**

**中段不存在**，因为"降滞后"和"保相位裕度"要求相反。这不是手感问题，是数学。唯一的出路是**积分项**（或精确标定的前馈），它能在不消耗相位裕度的前提下把 `e_steady` 压到 0。

### 10.3 用本工程真实参数的数值仿真

参数：目标 720 px/s，控制环 120 Hz，输出限幅 120 px/步。下表是**稳态峰峰误差**（px）：

| 延迟 L | 出厂 `Kp=0.50 Ki=0` | DsAi `Kp=0.35 Ki=6` | `Kp=0.25 Ki=2` | **`Kp=0.20 Ki=2`** |
|---|---|---|---|---|
| 4 步 (33 ms) | **530** 震荡 | **390** 震荡 | 0 | **0** |
| 5 步 (42 ms) | **771** 震荡 | **1164** 震荡 | 0 | **0** |
| 6 步 (50 ms) | **1009** 震荡 | **2012** 震荡 | 227 震荡 | **0** |
| 7 步 (58 ms) | **1246** 震荡 | — | 828 震荡 | **0** |

出厂配置（`Kp` 等效 0.5）在**每一档延迟下都在震荡**。这就是你按下"恢复默认"之后看到的"乱抖"，和你的手感无关。

`Kp=0.20 / Ki=2.0` 是唯一在**两倍延迟不确定度**范围内都安静、且稳态误差收敛到 **0** 的组合。注意它是**更小的 Kp + 非零的 Ki** —— 与"跟不上就加增益"的直觉相反。积分项接手了跟随速度之后，P 只需要处理残差，**小 Kp 才是买相位裕度的那笔钱**。

**积分项还会自动标定那个我们无法知道的量**：游戏的触摸灵敏度（手指 px → 画面 px）。仿真扫描 plant gain 0.5×~1.4×，稳态误差全程保持 0 —— 因为积分会一直累积到输出"够大"为止，不管"够大"是多少。**这就是你再也不需要猜那个魔法增益的原因。**

### 10.4 DsAi 那个 PID 行不行

**结构行，数字不行。** 逐条：

| DsAi 的做法 | 本工程缺不缺 | 结论 |
|---|---|---|
| **真积分**（`积分累计 += 误差*时间间隔`，Ki=6） | 缺。`predict` 默认 0 把 I 通道乘没了，而且那根本不是积分，是卡尔曼速度估计 | ✅ **必须抄** |
| **显式 dt**（`误差变化率 = Δe/时间间隔`） | 缺。控制器完全无 dt，而渲染环在 120 Hz / 60 Hz 两档之间真的会切 | ✅ **必须抄** |
| `已达标` 状态机（远时增益减半 / 积分慢累积） | 缺 | ⭕ 可选，本工程用输出限幅的 tanh 软饱和替代了"远距不过冲"的作用 |
| `微分输出 = atan2(微分, 50) * 200` 有界微分 | 缺 | ✅ 抄"有界"这个思想（本工程用 clamp） |
| `平滑因子` 真 EMA | 缺（旧"平滑"是伪装成平滑的增益） | ✅ 补上，但**默认关** —— EMA 加相位滞后，而相位滞后正是延迟环唯一付不起的东西 |
| `PID pid_x(0.35, 6, 0.004)`，`dt=0.005` | — | ❌ **不能照搬** |

不能照搬的原因：**DsAi 是 200 Hz 的 PC 鼠标环**，`dt=0.005`，延迟只占几个采样；`Kp=0.35 / Ki=6` 在 L≥4 时全部落在振荡区（见 §10.3 仿真表）。本工程是 120 Hz 触摸环，跑着 capture→推理→后处理→uinput→游戏自身输入延迟，L=4~7 步。

另外值得一提：DsAi 自己把 **PID** 和 **提前量** 拆成了两个模块，`提前量` 只动瞄准点偏移。这反过来说明本工程把 `延迟补偿`（位置前移）和 `速度前馈`（位移叠加）同时打开是设计错误 —— 两者数学上进入同一个通道，默认值 1.0 + 1.0 时等效给手指加了约 **1.5×** 目标速度，而真正需要的只有 1×，多出来的 0.5× 就是"过冲"。

### 10.5 本轮改动

1. **控制器内核换成 DsAi 结构**（`tracking/pid_controller.h`）：P（按步，不乘 dt）+ **真积分**（按秒累积、以输出限幅为钳位）+ 有界微分 + 可选输出 EMA。默认 **Kp=0.20 / Ki=2.0 / Kd=0.004 / 输出平滑=1.0(关) / 输出限幅=120**。
2. **修掉重复的速度补偿**：`延迟补偿` 默认 `1.0 → 0.0`；`速度前馈` 成为唯一的速度旋钮（上限 2→3）。
3. **控制器接入 dt**（`io.DeltaTime`），并给 120 Hz / 60 Hz 两档做归一化。
4. **遥测日志**：每 480 个控制步打一行 `AimbotNg: aim: mean e=(..) pid=(..) ff=(..) dt=..ms`。**`e` 恒一个符号 ⇒ 滞后；`e` 来回变号 ⇒ 振荡** —— 这两个从此不用猜。
5. **配置迁移**：`kp`/`kd` 单位变了，旧存档的 `kp=25` 会被判为非法并**回落默认**（否则 clamp 到 1.0 正好是最坏值）。

### 10.6 调参流程（第三版）

1. 恢复默认：`Kp=0.20`、`Ki=2.0`、`Kd=0.004`、`输出限幅=120`、`输出平滑=1.0`、`速度前馈=1.0`、`延迟补偿=0`、`死区=0`。**先别动任何一个。**
2. 看 logcat 的 `aim:` 那行：
   - `mean e` **来回变号** ⇒ 还在振荡 ⇒ 降到 `Kp=0.15`、`Ki=1.0`；仍振荡 ⇒ 你的环路延迟 >7 步，问题在延迟本身（capture/推理帧率），不在增益。
   - `mean e` **恒一个符号** ⇒ 有滞后 ⇒ 加 `Ki`（2 → 4 → 6，每加一次看是否变号）。
3. 只有在 2 稳定之后，才动 `速度前馈`（让积分负担小一点，收敛更快）。
4. `Kp` 是最后才碰的旋钮，每次 +0.05。
5. `输出平滑` 除你有明确需要，保持 1.0（关）。

## 11. 第四轮：真正的根因——控制器每帧被复位（2026-09-20 深夜）

### 11.1 现象与它为什么推翻了前三轮的假设

用户提供的三个事实：**游戏 120 帧、截图 120 帧、推理 2ms**。

这三个数字把"延迟"从嫌疑名单里划掉了——capture→推理→后处理的整条链只有十几毫秒，检测框确实"没多少延迟"，与观察一致。既然如此，剩下的只可能是控制器本身。

用户的原始描述有三条，且互相矛盾到无法用单一增益解释：

- 自瞄**永远**跟不上，不是"慢一点"
- `Kd` 拉到 0 反而**不震**
- `Kd` 拉一点点就**来回甩**

一条 P 律无法同时产生"永远跟不上"和"Kd 一动就震"——除非 **Kd 根本不是阻尼**。

### 11.2 根因：一行

```cpp
// ui/gui/sections/aim_section.cpp  syncAimPage()  —— 每个渲染帧都执行
p.touchAim.aim.init(p.kp.value, p.ki.value, p.kd.value,
                    p.outSmooth.value, p.smooth.value);
```

```cpp
// tracking/pid_controller.h  （修复前）
bool init(float kp_, float ki_, float kd_, float outSmooth_, float limit_px_) {
    kp = kp_; ki = ki_; kd = kd_;
    outSmooth = ...; limitPx = ...;
    reset();          // ← integral = 0; lastError = 0; outPrev = 0;
    return true;
}
```

`init()` 本意是"把滑条值推给控制器"，却以 `reset()` 收尾。它每秒被调用 120 次。

**后果 1 —— 积分是死的 ⇒ 永远跟不上**

`integral` 每步归零，于是 I 项退化成 `ki · e · dt` 的单步值，即一个极小的第二比例项。环路从二阶降为一阶比例律，对匀速目标有**固有稳态误差**：

```
e_ss = v / (sens · kp)
```

`v = 12px/帧`、`kp = 0.2` 时是 60px —— 一个身位。**它不会随 Kp 增大而消失，只会换成振荡。**

**后果 2 —— `lastError` 每步归零 ⇒ D 项变成隐藏比例增益**

`d = kd · (error − lastError) / dt`，而 `lastError ≡ 0`，故：

```
d = kd · e / dt        ⇒ 等效比例增益 = kd / dt
```

| kd | 60Hz 等效增益 | 120Hz 等效增益 |
|-----|--------------|---------------|
| 0.001 | 0.06 | 0.12 |
| 0.004（出厂）| 0.24 | **0.48** |
| 0.008 | 0.48 | 0.96 |

所以 `kd = 0.004` 时**总比例增益 = 0.20 + 0.017 + 0.48 = 0.70**（120Hz），而该帧率下 L=4 的稳定上界只有 0.35。用户拉动"阻尼"滑条，实际是在拉一根**没有刻度的增益线**：

- 拉到 0 ⇒ 增益 0.23，低于上界 ⇒ 不震，但积分是死的 ⇒ 恒定滞后
- 拉到一点点 ⇒ 增益越过上界 ⇒ 来回甩

**"kd0 反而不震"不是巧合，是唯一正确的读数。** 前三轮一直在增益和单位上打转，因为真正的病在状态被清空，而状态不可见。

### 11.3 修复

| # | 改动 | 位置 |
|---|------|------|
| 1 | `init()` → `setGains()`：**纯赋值，永不复位**。复位只由新交战（Idle→Pressed）显式调用 | `pid_controller.h` / `aim_section.h` |
| 2 | Kalman 重同步时 `lastError = error`（原来置 0），否则 D 项在重同步后打出一个 `kd·e/dt` 的冲击——正是那个分支想避免的突跳 | `pid_controller.h` |
| 3 | 死区**只冻结积分**，不再让积分在被丢弃的输出背后继续累积（抗积分饱和）。误差仍原样进入 P/D，`lastError` 保持连续，避免跨死区边界时 D 项尖峰 | `pid_controller.h` / `aim_section.cpp` |
| 4 | **手指重锚不再清控制器**：`maxDragDist`(400px) 触发抬起时置 `carryTrim`，`press()` 据此跳过 `reset()`。400px 在 720px/s 下约 0.55s 触发一次——积分每半秒被清一次，等于没有积分 | `aim_section.h` / `aim_section.cpp` |
| 5 | **瞄准时渲染层跑满帧**：新增 `sections::aimIsDriving()`，渲染分级里插在 detector 档之前 | `aimbot_ui.cpp` |
| 6 | 增益按新语义重设：`kp 0.20→0.30`、`ki 2.0→1.0`、范围 `0~15→0~4`；`kd 0.004→0.002`、范围 `0~0.02→0~0.008` | `aim_section.h` |
| 7 | 配置加 `ctl` 版本号（`kCtlSchema = 3`）：增益语义一变就重新播种。旧文件里的 `kd=0` 是被抖动逼出来的，携带它等于静默丢掉阻尼 | `config_manager.cpp` |
| 8 | `aim:` 日志加入 `trim` —— 积分值是整个自瞄里最有诊断意义的数字 | `aim_section.cpp` |

### 11.4 为什么第 5 条与"跟不上"有关

`kInferenceFps = 60` 把**整个渲染层**压在 60fps，而 `syncAimPage()` 跑在渲染层里。于是：

- 手指每 16.7ms 才动一次 ⇒ 720px/s 的目标每帧要跨 12px ⇒ **台阶感**（用户说的"不丝滑"）
- 环路延迟**按帧计**：帧长减半，毫秒延迟减半，相位裕度翻倍 ⇒ 可用 Kp 上界提高
- tracker 也在同一处被喂：60fps 只看到一半的 120fps 检测结果

检测器需要 60 帧，自瞄需要满帧，取大者。代价只是瞄准期间覆盖层自己的重绘，松手即回落。

### 11.5 数值验证（120Hz 控制 / 1Hz ±200px 正弦横拉 / ff=1.0）

| 配置 | RMS 跟踪误差 | 峰峰 |
|------|------------|------|
| 修复前 `kp.20 ki2 kd.004` | 197 | 771 ← 振荡 |
| 修复前 `kd=0`（用户被迫的选择）| 179 | 474 ← 稳定但恒定滞后 |
| **修复后 `kp.30 ki1 kd.002`** | **10.2** | **29** |

kd 可行性扫描（RMS，L=2/3/4/5）：`kd=0` → 462/617/744/826；`kd=0.002` → 406/559/696/794；**`kd≥0.01` 全部振荡**。所以 120Hz 下 kd 的可用区间是 `0 ~ 0.006`，滑条上限据此定为 0.008。

`ki` 扫描：`ki=4` 在 L≥3 不稳定；`ki=1` 在 L≤4 全程稳定且稳态误差为 0 —— 积分只负责**配平**（消除残差、吸收未知灵敏度），不负责带宽。

### 11.6 调参流程（第四版，最短）

1. 恢复默认：**`Kp=0.30`、`Ki=1.0`、`Kd=0.002`、`输出限幅=120`、`输出平滑=1.0`、`速度前馈=1.0`、`延迟补偿=0`、`死区=0`**。先原样用。
2. 看 `logcat -s AimbotNg | grep aim` 的 `trim`：
   - `trim` **恒为 0** ⇒ 积分又被某处清掉了（回归 bug，回来找我）
   - `trim` 停在 ±120 ⇒ 饱和，`Kp` 太小或灵敏度极低
   - `trim` 在 ±10~±60 之间随目标速度起伏 ⇒ **正常，这就是它在干活**
3. `mean e` **来回变号** ⇒ 降 `Kp`（0.30 → 0.25 → 0.20）；**恒一个符号** ⇒ 升 `Ki`（1 → 2 → 3），每次只动一格。
4. 稳定之后再用 `Kd` 收尾：0.002 → 0.003 → 0.004，**感觉到抖就退回上一档**。120Hz 下超过 0.006 必震。
5. `速度前馈`：还落后 → 1.1~1.3；冲过头 → 0.8~0.9。

> 一句话记住这次：**先确认控制器"有记忆"，再谈调参。** 一个每帧被复位的控制器，任何增益都只在描述它坏掉的方式。

## 12. 第五轮：单位与边界修复（v4 控制器）

### 12.1 症状与判决

用户报告：延迟补偿等调零、`kp=0.2`，**移动非常慢，但会晃两下，幅度大且慢**；`kd` 一碰就抖，"可以当成没有这个参数"。

三个症状看似矛盾（既慢又晃），实际上是**同一个判决的三种表现**：环路已经在稳定边界之外，靠输出限幅兜着走极限环。

- **又慢又晃** — 环路越过稳定边界 ⇒ 限幅饱和 ⇒ 极限环。手指被反复甩到 ±限幅，净位移接近零（"非常慢"），而每次过冲都有几百像素（"晃"）。仿真里旧控制器在 α=1.0/L=7 处峰峰 1400px、α=1.6/L=7 处 2038px，且**不衰减**。
- **kd 一调就抖** — 旧 `kd` 是**每秒**单位，代码里 `d = kd·Δe/dt`，所以它对**单步误差变化**的系数是 `kd/dt = kd×120`（120Hz）。滑条标称 0~0.008，在 120Hz 下的真实系数是 0~0.96、奈奎斯特增益 0~1.92。**标签小了 120 倍**，于是：可用区间挤在滑条最底下一小段（"没这个参数"），而第一个生效的档位已经能放大噪声（"一调就抖"）。它唯一能反应的是**换目标**——两个敌人中心相距约 100px，一步跳过去，`kd=0.002` 就打出 24px 的手指踢动。**既哑又吵。**

### 12.2 四处结构性缺陷

| # | 缺陷 | 后果 | 修复 |
|---|------|------|------|
| 1 | `kd` 是每秒量纲，`/dt` 让它变成 120 倍隐藏增益 | 滑条语义与标签差 120 倍；奈奎斯特增益无上界 ⇒ 阻尼与噪声放大同时到达 | `kd` 改为**每步**无量纲（与 P 项同一约定，且帧率无关：奈奎斯特增益恒为 `2·kd`）；**微分加一阶低通**（`kDerivTauSec=25ms`）限住高频增益 |
| 2 | 积分上限 = 输出上限（120px/步 ≈ 14400px/s） | 逼近时积分顶到上限，随后**退绕极慢**（只有 `ki·e·dt` 在拉它，而接近目标时 e 很小）⇒ 幅度大、频率低的晃 | 积分独立上限 `kTrimLimitPx=24`；**条件积分**（输出已饱和且误差还想往外推时不累积） |
| 3 | 输出限幅是滑条 | 它从来不是调参量，却被用户当旋钮拧，掩盖了真实的极限环幅度 | 硬编码 `kOutLimitPx=60`（≈7200px/s，约为人类甩动上限的 2 倍，300px 修正仍只需 42ms）；滑条删除 |
| 4 | **前馈增益的量纲是错的** | 前馈按 `vx × gain` 叠加，而手指要走 `vx/α` 才能让视角移动 `vx`。正确增益是 **1/α（游戏灵敏度）**，默认 1.0 时整体差 α 倍 | 范围扩到 0~6（覆盖 α≥0.17）；上限与输出限幅同值；文档改为"**标定量**" |

另加两条配套修正：

- **换目标判定改由轨道 id 驱动**。原来在控制器内部用"误差一步跳超过 220px"猜，两个方向都错：**大摆幅（正是极限环的样子）每半个周期就触发一次，把本该阻尼它的积分清掉**；而两个相邻敌人（约 100px）的常见切换又够不着阈值。现在由调用侧比对 `trackId`。
- **瞄准期间不再把面板刷新率投票交还**（`aimbot_ui.cpp`）。原来菜单一隐藏就投 0，而那正好是用户真正开火的时候。环路延迟**按帧计**：帧率减半 = 延迟秒数翻倍 = 相位裕度减半 ⇒ 菜单打开时调好的增益，一隐藏菜单就开始振。

### 12.3 数值验证（`scripts/aim_loop_sim.py`）

该脚本是 `pid_controller.h` 的逐行移植，跑在 (α, L) 参数网格上——α（视角px/手指px）和 L（延迟步数）是**两个没人知道的量**，所以只能挑"整格都安静"的参数，而不是某一格最快的。

**滤波后的"每步" Kd 是这一轮的关键收益**（阶跃响应尾段振铃峰峰，α∈[0.3,1.6] × L∈[6,8] 共 15 格）：

| kp | kd | 振铃格数 | 最大振铃 |
|----|-----|---------|---------|
| 0.10 | 0（旧式） | 6 / 15 | 1044 |
| 0.10 | **0.35（本版）** | 2 / 15 | 730 |
| 0.08 | **0.35（本版）** | **0 / 15** | 12 |

Kd 终于在做微分该做的事——**买相位裕度**，而这是延迟受限环路唯一的硬通货。旧的每秒式做不到：在需要裕度的频段上它的幅值 `kd·ω` 可以忽略。

**前馈尺度是第二大发现**（0.6Hz ±250px 横拉，L=6，RMS 误差 px）：

| α | 0.3 | 0.6 | 1.0 | 1.6 |
|---|-----|-----|-----|-----|
| 前馈 = 0 | 111.2 | 40.6 | 22.1 | 119.5 |
| 前馈 = 1.0 | 74.6 | 17.0 | 4.1 | 121.5 |
| **前馈 = 1/α** | **19.0** | **7.5** | **4.1** | **2.6** |

**尺度正确的前馈在每个 α 上都砍掉 51~84% 的跟踪误差，比 kp+ki+kd 加起来还值钱。** 这就是"永远慢半拍"的真正来源，而它不是积分的活——积分要按秒爬到一个新速度，前馈在第一帧就给到。

> 自动标定版（用 `scale += mu·dt·(I/v)` 把积分驱到 0）已实现并验证收敛（α=0.3→3.64 目标 3.33；α=1.6→0.67 目标 0.62），但**没有采用**：标错的前馈会反向过冲，而一个用户看得见、能自己设的旋钮，胜过一个他看不见的估计器。留作后续选项。

### 12.4 新默认值

| 参数 | 默认 | 范围 | 说明 |
|------|------|------|------|
| `Kp` | **0.10** | 0~0.6 | α≤1.3、L≤8 全程安静；这是"快慢"旋钮 |
| `Ki` | **1.0** | 0~4 | 只负责稳态配平 |
| `Kd` | **0.35** | 0~2 | 每步、无量纲；0.35 是全网格安静的那一档 |
| `输出平滑` | 1.0 | 0~1 | 1.0 = 关（EMA 是纯相位滞后，延迟环付不起）|
| `延迟补偿` | 0 | 0~5 | 可选的额外领先 |
| `速度前馈` | 1.0 | 0~6 | **标定量 = 1/α** |
| `预测帧数` | 3 | 0~30 | 丢框外推 |
| `死区` | 0 | 0~1 | 静止目标嗡嗡响时给 0.1~0.3 |
| ~~`输出限幅`~~ | — | — | **滑条已删**，常数 60 |

### 12.5 调参流程（第五版）

**只动两个数，按顺序。**

1. **全部恢复默认**（升级后第一次启动会自动重新播种，日志里有 `config: aim gains re-seeded ...`）。

2. **先定 `Kp` —— 稳定边界标定**（约 30 秒，每个游戏/灵敏度只需做一次）
   - 对着一个**站着不动**的目标，把 `Kp` 从 0.10 往上加（0.15 → 0.20 → 0.30 …）。
   - 找到**刚开始左右摆**的那一档，然后取它的 **60%**。例：0.25 开始摆 ⇒ 定 **0.15**。
   - 判据在日志里：`mean e` 在目标静止时**来回变号** ⇒ 摆；恒定趋近 0 ⇒ 稳。

3. **再定 `速度前馈` —— 灵敏度标定**（每个游戏/灵敏度一次，收益最大）
   - 对着一个**持续横移**的目标。看准星：
     - **一直落后** ⇒ 调大（1.0 → 1.5 → 2.0 → 3.0 …）
     - **冲到前面 / 目标一掉头就过冲** ⇒ 调小
   - 停在"既不落后也不超前"的那一档。这一档数值上就是 `1/灵敏度`。
   - 日志判据：`trim` 随目标速度起伏但**不顶到 ±24**。

4. `Ki` 只在**稳定横移仍留有一小段固定滞后**时才动（1.0 → 1.5），一次一格。

5. `Kd` 收尾：0.35 是默认且通常就够。**只有在第 2 步标定后仍感觉"过冲后要摆一两下"时才加到 0.5~0.7。** 现在它是真的微分了，加了应该有正效果；没效果就别加。

6. **不要动** `输出平滑`（保持 1.0）和 `延迟补偿`（保持 0）。

**读日志**（`logcat -s AimbotNg | grep aim`，每 4 秒一行）：

```
aim: id=7 mean e=(3.2,-0.4) pid=(4.1,0.2) d=(1.8,-0.1) trim=(9.4,0.3) ff=(2.1,0.0) dt=8.3ms
```

- `id` 一秒变好几次 ⇒ **选靶问题，不是控制问题**，任何增益都救不了
- `mean e` 变号 ⇒ 摆（降 Kp / 加 Kd）；恒定同号 ⇒ 滞后（加前馈）
- `d` 恒为 0 而目标在动 ⇒ 微分没在干活
- `trim` 顶在 ±24 ⇒ 饱和，前馈太低或 Kp 太高
- `ff` 恒为 0 而目标在动 ⇒ 轨道速度估计断了（关联失败）

> 这一轮的教训与上一轮同源：**先把旋钮的单位和边界做对，再让用户调。** 上一轮是控制器没有记忆，这一轮是三个增益分属三套量纲、且积分可以借到整个执行器的权限——两次都不是用户"不会调"。
