## 1. 弹道分析到底是怎么出来的

### 1.1 输入是一段视频，不是静态图片

后坐力不是「一个位置」，是**一条随时间的轨迹**。单张静态图只能给出一个点，连「枪口是往上抬还是往下压」都定不了。所以最少要两帧，实际要**一整梭连射**：从满弹夹第一发之前，到最后一发之后几帧。

代价是录制有要求 —— 因为要测的是「视角运动」，任何其它让视角动的东西都会污染测量。

### 1.2 分析器内部做了什么

1. **逐帧跟踪墙面标记**：取第 0 帧的标记区域当模板，对每一帧做归一化互相关（NCC）匹配，再对相关峰做抛物线拟合拿到亚像素位置。**始终与第 0 帧比**，所以不会逐帧漂移。
2. **准心位移 = −标记位移**。视角旋转会让所有世界点在屏幕上等量反向移动，所以标记的屏幕位移取负就是准心的位移。枪模型、枪身后坐、FOV punch 都不影响，因为我们跟的是墙。
3. **逐发时刻**：默认用弹药计数（PaddleOCR 逐帧读数，计数第一次减一那帧算一发）；另有两种更轻的方法：弹药 ROI 帧间差峰（`ammo`）、枪口亮度峰（`muzzle`）。三种方法解到同一组发序，所以后面的 RPM 与弹道完全一致。
4. **单位换算**：针孔模型 `focal_px = (H/2)/tan(fov/2)`，`度 = atan(Δpx/focal_px)`，`cm = 距离·Δpx/focal_px`。
5. **输出**：逐帧 `trajectory` + 逐发 `pattern`（相对第一发）+ `rpm` + 质量字段（`tracking.min_confidence`、`ocr.shots_match_magazine`、`recoil_class`）。

### 1.3 录制协议（照做就行）

1. 训练场找一面平整、**有纹理**的墙，站定，距离保持一致。
2. 墙上贴一个**高对比小标记**（或选墙面已有的高对比小块）。放在画面偏一侧、且**偏上半屏** —— 后坐力会把画面往下推，留出余量让它整梭不出画。别放在准心或枪口闪光附近。
3. **关掉自瞄、关掉压枪、关掉陀螺仪、关掉游戏自带的辅助瞄准。** 这是最重要的一条：分析器要求「视角里只有后坐力」，否则你测到的是「后坐力 + 自瞄补偿」的合成量，拿去驱动压枪会**双重补偿**。
4. 手机端怎么开火都行，只要不动视角：用 **Trigger 页自动点按开火**（最省事，且落在触摸区域的随机点，不会碰视角区），或者一根手指按住开火键、开火期间手不碰视角区。
5. 录屏（手机自带录屏即可），然后**首末帧裁准**：起始帧 = 满弹夹还没开第一发；结束帧 = 最后一发之后几帧。PC 上用 LosslessCut 逐帧裁（流拷贝，不重编码）。
6. 分析器 GUI 里画框：**墙上标记（必需）** + **弹药计数**（用于逐发时刻，可选但强烈建议）+ 可选箱体（交叉校验）。导出 JSON。

### 1.4 手机端的三个实操要点

- **帧率越高越好。** 60 fps 下每发间隔量化到 16.7 ms，720 RPM 的 83.3 ms 会读出 ±10% 的时序误差 —— 形状不受影响，但重同步锚点会差。能 120 fps 就 120 fps。
- **录屏本身会掉帧**（编码开销）。别同时开画质增强/高码率；录完核一下总帧数与时长对不对得上。
- **FOV 填错不致命，只要一致。** px → 度只差一个标量（`focal_px`），而它最终被整梭行程 S 吸收；x/y 用同一个 focal，所以**形状不受影响**。真正要守的是：**所有枪用同一套 FOV/距离设置录**，否则 α 不能跨枪复用。距离只影响 cm，我们用不上。

### 1.5 入库闸门

不合格的档案不要进设备：

- `recoil_class` 必须是 `"standard"`。`"recovers_between_shots"`（左轮类）的 `pattern_spread` 是测量噪声底不是后坐力，拿它做压枪会把「本来就归零」的枪往下压。
- `tracking.min_confidence` 要接近 1.0（掉了说明标记物出画或被糊掉，那几发作废）。
- `ocr.shots_match_magazine` 应为 true。

## 2. 你给的两份东西，各自值什么

### 2.1 `trajectory_mover.cpp`

它写的是「3D 航点 → 平滑曲线 → 匀速前进 → 到达判定」，跑在 PC 上当仿真器。**3D、Catmull-Rom、CLI、CSV 导出、到达半径全是包袱**，真正可搬运的只有 `TrajectoryMover` 里这几十行：

| 现有实现 | 压枪里对应什么 |
|---|---|
| `Leg{ samples, cumDist, length, speed }` | 一段弹道：起点终点 + 这一段该用多久走完 |
| `leg.speed = baseSpeed * waypoint.speedFactor` | 每段速度 = 段长 / 该发间隔（`speedFactor` 天然对应非匀速射速） |
| `update(dt)` 里 `tRemaining -= distToEnd / leg.speed` | **帧率无关的关键**：一帧的 dt 跨过段边界时，余量带到下一段继续走 |
| 二分查 `cumDist` + `lerp` | 按时间取本项目前该在哪儿 |
| `reachRadius_` | ⚠ **必须设 0**。带到达半径会让每段提前吸附，把阶梯压扁 |

**要纠正的一点：不要用 `--smooth`。** 后坐力是**逐发台阶**，不是曲线；逐发采样点之间的真实运动是线性的。Catmull-Rom 是插值样条但在结点间距不均时会**过冲**，而 AKM 弹道恰好是先上、再右、再上的折线 —— 过冲的那几帧就是「多拖了」。分析器给的 `trajectory` 已经是 120 fps 采样的真值，降到 ~10 ms 一个结点后本身就分段光滑，再插值只会引入误差。

结论：**照抄 `update(dt)` 的积分结构，插值换线性，`reachRadius_` 置 0，丢掉 Vec3 与曲线。**

### 2.2 `recoil-analyser`

PC 侧离线工具（cv2 + PaddleOCR + Tkinter），**不能也不该搬到设备上跑**：OCR 与 cv2 太重，116 Hz 实时更不可能；而后坐力图谱是**武器的静态属性**，录一次用一辈子。

用它时有一个非显然的选择：JSON 里同时有 `pattern[]`（逐发，34 条）与 `trajectory[]`（逐帧，403 条）。

- `pattern` + `rpm.intervals_frames` = 逐发阶梯 + 每发时刻 → **重同步锚点**与总量换算。
- `trajectory` = 逐帧视角路径（**真值**），含发间蠕动与回位 → **形状**。

单靠 `pattern` 会丢掉发间蠕动；单靠 `trajectory` 拿不到「第几发」这个锚。两个都要。

## 3. 核心：唯一真正的未知量 α，以及「一个旋钮」

- `θ(t)` = 视角自第一发起累计转过的角度，单位**度**，`+x 右 / +y 下`。
- `α` = 玩家当前灵敏度下，每 1 finger px 产生多少度旋转（度/finger px）。
- `c(t)` = 我们要施加的补偿，单位 finger px。

要抵消后坐力，就是让「游戏转的 + 我们转的 = 0」：

```
c(t) = − θ(t) / α
```

`θ` 的 y 分量为负（枪口上抬 ⇒ 视角上转 ⇒ 屏幕内容下移 ⇒ 标记下移 ⇒ 准心上移 ⇒ y 负），所以 `c.y` 为正 —— **补偿就是往下拖**。X 同理：弹道往右漂则补偿往左。

`θ` 是**武器的固有属性，与灵敏度无关**；`α` 是**玩家的设定，与武器无关**。只有 `α` 未知。

### 取消掉 α：把旋钮定义成「整梭行程」

令 `Θ = |θ(末)|`（这一梭总共要转多少度，档案里就有），用户只调一个量：

> **整梭行程 S**（finger px）——「这一梭打完，一共往下（往左/右）拖多少像素」

```
c(t) = − (S / Θ) · θ(t)
```

- 用户不需要知道 α，也不需要知道 Θ。就是「拖多远」。
- `S = Θ / α` ⇒ **`α = S / Θ` 与武器无关**，存成「当前游戏 + 当前灵敏度档位」的属性。
- 换枪时 `S = α × Θ_新枪` **自动给出**，不用再调。**N 次调参 → 1 次。**

附带自检：几把枪反解出的 α 若明显不一致，说明游戏对每把枪有独立后坐乘子（或其中一把是开镜录的，FOV 不同）—— 这时 α 不能跨枪复用，退化为逐枪调 S。

**这也解释了为什么「强度」必须是乘在整条曲线上的标量**：形状对就够，幅度错了只是整体偏一点，不是形状错。而幅度错这一点，自瞄开着时反馈还会补掉（§7.4）。

## 4. 两轴：你要压水平是对的，但 X 轴要「让」出来

### 4.1 为什么压水平才是刚需

垂直后坐力人手能自己解决 —— 一直往下拖就行，方向是已知的、可控的。水平漂移不可预测：你不知道第几发会往哪边摆，也就无法用手补。**自动化的价值恰恰在 X。** 参考量级（AKM 实测 @1440p）：水平 spread 41 px，垂直 245 px —— X 的**量级小**但**难在人不知道往哪边**。

### 4.2 X 轴和现有环路的关系

X 是现有环路里**唯一有载波、会极限环**的轴（Y 有停止带 `boxHalfH` 与抬高一带高的静息泊位，`v_y ≡ 0`）。往 X 上以射速频率（720 RPM ⇒ 12 Hz）注入开环信号，会喂进环路里。

### 4.3 ~~处理：压枪激活期间让出自瞄 X 轴~~ —— R3 已删

> **作废。** 用户判断：「开火期间让出自瞄水平轴有什么用处，直接删掉」。复盘下来这个判断是对的，删掉的理由比当初加它的理由更硬：
>
> 1. **压枪不改变自瞄看到的误差。** 补偿是加在**触点位置**上的，自瞄下一帧读到的框心是「已经压过的画面」，误差天然就是补偿后的残差 —— 不存在「两者往相反方向拖」的互斗，§7.4 担心的对抗本来就不成立。
> 2. **让轴会丢掉载波。** R22 之后移动目标的载波来自预测项 `lookahead · v̂`；冻结 P/D 只丢修正，但积分被暂停后**松手那一帧带着陈旧值弹回来**的风险是真的（原方案要用「启动帧清积分」打补丁，补丁本身就是症状）。
> 3. **开火期间正是最该跟枪的时候。** 打移动目标时让出 X 轴 = 交火中放弃水平跟随，为了一个不存在的互斗付这个代价不划算。

原实现（保留以便回退）：复用现有 `step()` 的逐轴冻结参数（`aim_section.cpp:413` 的 `xInDz`），把压枪激活 OR 进去，**零成本**。

冻结的语义（见 `predictive_pid.h` 头注）：**压制 P 与 D、暂停积分的累加，不动预测项**。而 R22 之后：

- 预测项（`lookahead · v̂`）才是移动目标的**载波**；
- 积分已降级为「残差清理器」。

所以让出 X 轴丢掉的只是误差修正那一小块，**移动目标照跟**。附带收益：开火期间水平不再抖（载波被让出）。实现细节：压枪启动那一帧把 X 积分清零，避免它带着开火前的陈旧值在松手后弹一下。

### 4.4 行程预算的影响

只压 X 时，整梭补偿量是**几十 finger px** 量级，离 `maxDragDist = 400 px` 很远 ⇒ §7.2 的最大风险基本消失。两轴同开时风险回来（垂直 16.2° 在低灵敏度下可达 ~405 fp px）。

## 6. 方案分级

### A. 纯开环（v1）
档案 + 开火时刻 → 回放 → 偏移。**不需要采集管线、不需要模型、不需要 OCR。**
- 优点：改动面最小、最不容易伤到现有链路、可以先把「标定」这个最大风险验证掉。
- 代价：幅度靠一个旋钮；射速与档案不符时会漂。

### B. 开环 + 逐发重同步（v3）
在 A 之上加逐发检测，每检测到一发就把回放索引对齐一次。
- 信号源（由便宜到贵）：`muzzle` 枪口亮度峰 → `ammo` 弹药 ROI 帧间差峰。**不需要 OCR**，只要「什么时候变了一下」。
- 代价：弹药计数器在屏幕底部，**不在现有采集裁剪里**（`capture/capture.h` 是屏幕中心方裁）。producer 侧（`ScreenCapture.kt`）本来就是整屏镜像，多发一块小 ROI 即可（第二次拷贝，开销可忽略）。
- 收益：修掉射速漂移，支持点射 / 换弹 / 残弹 / 非等间隔射速。

### C. 真闭环（视觉测横移）—— **不做**
跟踪固定世界特征、逐帧测横移、闭环压到零。听上去最漂亮，**不成立**：它测到的是「总视角运动」，里面混着**玩家自己手指**的瞄准和**敌人**的位移，没有先验无法分离。玩家当时手就按在视角区（在瞄），闭环会去对抗玩家。
退一步只在融合接管时才诚实 —— 而那正是自瞄环路本身在做的事。其价值被 A 吸收为「前馈 + 现有 PID 反馈」。

**推荐：A → B。C 不做。**

## 7. 风险与交互（按严重度）

### 7.1 α 未知（中）
首次使用要调一次 S。缓解：单旋钮、30 秒调完、反解复用；自瞄开着时反馈补掉幅度残差（§7.4）；后续可用 `aimf` burst 遥测回归 α（斜率 = −α）给默认值。

### 7.2 手指行程预算（只压 X 时低；两轴同开时**高**）
`aim_section.h:149 maxDragDist = 400.0f`：合成手指离按下点超过 400 px 就 lift + repress。垂直满梭在低灵敏度下可达 ~405 fp px，正好撞线 ⇒ 可能**打断开火**。镜像路径（③）更没有重锚手段，只能被屏幕边界截断，而截断之后**内部记账仍以为动到了**，必须显式处理。
缓解（三条都做）：① 压枪激活期间放宽（或对压枪位移单独记账，不累进拖拽安全判据）；② 合成手指**锚在高处**，给向下预算留整屏高；③ 累计量接近边界时**停住并打日志**（`recol: clamped`），宁可压不住也不要跳。

### 7.3 开火起点对齐（中）
`t=0` 是「第一发打出去」，触发信号是「手指按下开火区域」，中间有游戏自己的上膛/开火延迟。
> **R3：`起始延迟 ms` 滑条已删**（用户判断「没啥用的感觉」）。对齐改由§4 方案 B 的**重同步**自然消掉 —— 比一个要手调的数字更省事，也不占一行 UI。

### 7.4 和自瞄环路的关系（低）
直觉担心「压枪往左拖、PID 又给拖回去」。实际不会：前馈**同一帧**生效，PID 有约 12 帧延迟（`kPredSamples 4 + kPredStableReady 1 + 两级卡尔曼`）。瞬态由前馈赢，等 PID 反应过来误差已经很小。**幅度只要在 ±50% 以内，反馈就把残差抹掉** —— 这同时是 §7.1 的缓解。加上 §4.3 让出 X 轴，两者是互补而非互斗。

### 7.5 反检测（中）
「开火期间以恒定速率横拖、且抵消得完美」是人手做不到的。复用已有的人类化手段（`press()` 的 ±jitter、Trigger 页的上下波动思路），给补偿量加 ±1~2% 随机抖动与轻微速率起伏。

### 7.6 「开火后视角复位」语义（低，但结论反直觉）
有些游戏松手会把视角回正。直觉是「那我们也得把手指放回去」。**不要。** 我们的补偿在抵消游戏转的角度，净视角没动；此时把手指移回去等于主动把视角往反方向转一整条弹道。正确行为：**开火结束就停止产生，手指留在原地。** 触点对游戏是按位移消费的，留原地不会跳变，玩家接着拖也没有不连续。

## 8. UI 设计

### 8.1 你的布局成立，理由

左宽右窄的分配是对的，因为左边放**标量**（滑条要宽度、要反复试），右边放**对象与它的可视化**（下拉、按钮不需要宽度）。页面壳子用现有的：左侧导航第 8 项「压枪」，右侧内容区（标题 36 px + 发丝线 + 可滚动内容），滚动沿用 `Scroll& sc`（`sectionIsScrollable` 要为新页打开）。

**一个技术约束**：现有框架**每页只有一个滚动偏移**，由竖直拖拽手势驱动（`hud.cpp:632`）。所以两栏会是**同一个滚动**（内容高度取两栏较高者）。这在实践中没问题（两栏都短，通常根本不需要滚），但要知道它存在。

### 8.2 一处要改：图的宽度 —— R3 用**竖版图**解决（用户点名）

按你的分栏，右栏约 178 逻辑 px。弹道图**横着**放进去，横向可拖拽宽度只有 178 px —— 按每发一个结点、AKM 34 发算，**每发只分到 5 px**，手指点不中任何一个结点。而这张图是本次功能**唯一的核心操作对象**。

R2 给了三个选项（加宽右栏 / 展开按钮 / 改布局）。**R3 采用第四个、也是更好的一个：把图竖过来。**

> 用户原话：「弹道是竖着的不是横着的，竖着直观。」

关键在于这个直觉是对的，而且有硬理由：

| | 横版 | **竖版（已采用）** |
|---|---|---|
| 长轴 | 时间（发数）压在 178 px 的**短边**上 | 时间（发数）走**长边**，34 发 ≈ 每发 15+ px，点得中 |
| 短轴 | 水平漂移，被拉满整条宽 | 水平漂移，几十 px 的量级正好 |
| 与游戏画面对应 | 无 | **x 轴 = 画面的左右、y 轴 = 时间往下**，和「枪口往上抬、往两边摆」的直觉一致 |
| 微调方向 | 水平拖 = 改时间，反直觉 | **水平拖 = 改水平漂移**，方向即语义 |

竖版下 §8.2 的三个妥协选项全部作废：右栏不用加宽、不用展开态、布局不动。

### 8.3 微调的语义（这条最容易做错）

弹道是**累计位移曲线**。所以拖动第 k 个结点的物理含义是「第 k 发这一次的位移量不对」，它必须**对第 k 发之后的所有帧累加**（一个阶梯），而不是只把那个点挪走。只挪单点会在曲线上留下一个尖刺 = 物理上不可能的「瞬移一下又回来」。

- 图上同时画**两条线**：原始测量（虚线灰）+ 微调后（实线蓝）。少了原始线，改完就不知道偏了多少。
- 编辑粒度 = **逐发**（AKM 34 个点），不是逐帧（403 个点）。逐帧既画不清也点不中。
- 拖拽用现成的 `widgets::setWidgetDragging()` / `clearWidgetDragging()` 拿住手指，否则会被页面的滚动手势抢走（`hud.cpp:616` 的 widget latch 就是干这个的，滑条已经这么做了）。
- 拖动方向自由（水平/垂直都能拖），因为 X 和 Y 是两条独立曲线（或一张 2D 弹道图）。

### 8.4 存储：原始只读 + 微调叠加

原始档案（测量结果）**只读**，微调写成 `<name>.tune.json`。理由：测一次费一梭子弹 + 一套录屏裁剪流程，不该被手调覆盖掉。
- 「恢复」= 清空微调叠加，回到纯测量曲线。
- 「保存」= 写 tune 文件（标量 + 权重 + 开关 + 微调量）。
- 微调量以 **finger px 绝对值**存（不是按比例）：他观察到的误差是「这一发该往左 3 像素」，是绝对量；以后调 S 不该把它一起放大。

### 8.5 你的设计里缺的四样

1. **开火区域框选**（压枪的触发信号）。R3 已做：独立的 `RecoilFireArea`，复用 Aim 页触摸区域的拖拽/改边交互。**不借现有的「触发区域」** —— 那是自瞄的按住判定，语义不同（"我在开火" ≠ "自瞄在按手指"）。
2. **左右 / 上下翻转开关**。符号搞反是必踩的坑（弹道是在另一个游戏/另一套坐标约定里量的），一个开关比改代码快。R3 已做：`翻转X` / `翻转Y`。
3. ~~**「开火期间让出自瞄水平轴」开关**（§4.3）~~ —— **R3 按用户要求删除**，理由见 §4.3。
4. **轴权重 X / Y**。默认 X=1、Y=0。R3 已做。

**R3 又补了四样**（弹道分析集成带来的）：

5. **配置名输入框 + 录制/结束录制按钮**。R3 已做，见 §8.6。
6. **分析进度弹窗**。分析是分帧切片跑的（`kSlice=24` 帧/次），必须给用户看得到进度，否则「点了没反应」。
7. **标记框**（录制时跟踪的那个高对比图块）。设备上没有视频编码器（见 §8.6），录制走的是**实时 NCC 跟踪**，所以必须明确告诉它跟什么。
8. **自绘输入法**。配置名要支持中文，系统输入法在 overlay 上叫不出来、反射又麻烦 —— R3 自己画了一套 26 键 + 数字 + 拼音候选。

另外「整梭行程 S」旁边建议显示反解出的 α 与平均每发量 —— 这样跨枪复用是可验证的，而不是靠感觉。

### 8.6 机内录制与自动分析（R3 新增，替代「录屏 → PC 分析」）

用户要求：页面里有输入框存配置名、有录制按钮、**结束录制就自动分析**、分析有进度弹窗。

PC 那条链路（录屏 → `recoil-analyser` → `scripts/recoil_to_profile.py` → adb push）精度更高，但**每次换枪都要走一遍**，而枪是常换的。所以 R3 在设备上做了一套自助流程：

**硬约束：设备没有视频编码器。** 抓到的帧只在内存里活一帧，存不下来。所以「先录后分析」不成立，改成**边录边跟踪**：

1. **标记框**：用户在墙上找一处高对比细节（门框、标牌、石头），把标记框拖上去。框必须在**截图管线中心方块内**（页面会画出这个方块，所以"在里面"是看得见的，不是事后靠 log 猜的）。
2. **NCC 跟踪**：每帧在中心方块裁剪图里做归一化互相关（零均值 + 亚像素抛物线修正 + 粗搜再精搜），得到标记的位移 → 除以 FOV 换算 → 视角角速度 θ(t)。
3. **发数检测**：`|dθ|/dt` 超过「中位速率 × 4」且过最小速率 ⇒ 一发。发间最小间隔 34 ms（1800 RPM 上限）。
4. **回中判别**：发间运动 / 踢动 的中位比 > 0.7 ⇒ 判定为「发与发之间会回中」（`recovers_between_shots`），这类枪不能按阶梯累加来压。
5. **重采样**：10 ms 一个结点 → 写 `<name>.json` 进 profiles 目录。

全过程**分帧切片跑**（`kSlice = 24` 帧/次），不卡渲染；进度弹窗显示百分比与阶段（跟踪 / 找发 / 重采样）。置信度低于 0.30 直接判失败并说明原因（`TooLow`）。

> PC 那条路没删，仍是高精度备选：`scripts/recoil_to_profile.py`。

### 8.7 自绘输入法（R3 新增）

配置名要支持中文。两条路：反射调系统输入法（用户否决：麻烦）或自己画。**R3 自己画。**

- 标准 26 键 QWERTY + 数字/符号层 + 底行（123 / 中英 / ← / 空格 / → / 完成）
- 拼音候选条：内置 ~350 个音节表，空格上屏首选
- 圆角、配色走 `theme.h`、按下有位移+阴影的按压动画、长按删除连发
- 模态层归属：弹起时 `widgets::setModalOwner(true)`，`beginFrame()` 以「手势已消费」开局，所以敲键不会顺带触发底下的开关

## 9. 实施阶段与验收

**Phase 0（PC 侧，不动设备）**
`scripts/recoil_to_profile.py`：读分析器 JSON → 校验入库闸门（§1.5）→ 逐帧 px 换算成度（用 `focal_px`）→ 相对第一发 → 降采样到 ~10 ms 结点 → 输出档案 JSON；并且**在 PC 上先跑一遍回放**，把 `c(t)` 与 `θ(t)` 画在一张图上。
> 验收：符号与形态肉眼可判 —— 这一步就能抓住符号写反、`sample_frame` 相位错。**在设备上调试符号是浪费时间的。**

**Phase 1（设备，方案 A + 最小可用页面）**
`tracking/recoil_pattern.{h,cpp}`（抄 `update(dt)` 积分结构、线性插值、`reachRadius = 0`）+ 压枪页（导航 + 下拉选档案 + S + 延迟 + 轴权重 + 翻转 + 开关）+ 挂载点 ① ② + ④（120 Hz 档）+ ⑤（让出 X 轴）+ 遥测行。
> 验收：对着高对比标记打满梭，标记横向留在原位；`recol:` 行能看到逐帧补偿、累计量、档位。

**Phase 2（弹道图与微调）**
按 §8.2 (b) 做可展开的弹道图 + 逐发结点拖拽（阶梯语义）+ tune 文件读写 + 恢复/保存。
> 验收：改一发，曲线后半段整体错位（而不是出一个尖刺）；恢复后与原始线重合。

**Phase 3（挂载点 ③ + 行程预算）**
纯手动瞄准路径打通；§7.2 的三条缓解；边界钳制与日志。
> 验收：不开自瞄、纯手瞄，满梭不被打断，不出现触点跳变。

**Phase 4（方案 B：重同步）**
producer 多发一块弹药/枪口 ROI；检测峰 → 对齐 `shots_marks`。
> 验收：点射、半梭松手再打、换弹，都跟得上。

**Phase 5（自整定，实验）**
X 轴独有的优势：有目标框就有水平反馈。自瞄锁定、玩家手不在视角区时，**一梭内目标框的净水平位移 = 残差**。用一个**跨梭的慢积分**（不是帧级环路）修正 S 与微调量，几梭收敛。
> 这与 §6 方案 C 不同：C 是帧级闭环（会被玩家输入污染），这里是「一次交战 → 一个残差 → 慢修正」，混入的玩家输入跨梭平均掉。
> 验收：连打 5 梭，横向净漂移逐梭收敛。


## 11. 明确不做的

- **不把分析器搬到设备上**：弹道是静态属性，离线一次足够。
- **不做方案 C 的帧级视觉闭环**：测到的是总视角运动，混着玩家输入与敌人位移，无法分离。
- **不动 PID / 卡尔曼 / 推理**：压枪是叠加在触点上的一条独立通道，不经过任何控制器。
- ~~**不把分析器搬到设备上**：弹道是静态属性，离线一次足够。~~ → **R3 部分撤回**：视频分析器不搬（设备无编码器），但**机内实时标记跟踪 + 分析**已做（§12.2），因为「录屏→PC→push 回来」这条链路对用户太重。
- **不做「松手回中」**：会主动把视角往反方向转一整条弹道。
- **不做「放大人手拖动」**（把玩家自己的横拖乘增益）：不需要弹道分析，是另一个功能，本文档范围内不混。

## 12. R3 实装说明：参数与用处

页面：**导航第 8 项「压枪」**。总开关在**标题行右上角**（和别的页一样，没有「启用压枪」那一行）。

### 12.1 左栏：标量

| 控件 | 范围 / 默认 | 是什么 | 什么时候动它 |
|---|---|---|---|
| **配置名** | 文本 | 录制出来的档案叫什么，也用来选中它 | 录之前填。中英文数字下划线都可以（底部键盘支持拼音） |
| **开始录制 / 结束录制** | 按钮 | 见 §8.6。结束即自动分析，期间有进度弹窗；`取消` 放弃本次 | 换枪、换配件、换灵敏度时录一次 |
| **整梭行程·水平** | 0–600 fp·px，默认 220 | **唯一需要你试出来的数**。含义：这一梭打完，手指要往水平方向总共走多远 | 见下面「怎么调」 |
| **整梭行程·垂直** | 0–600 fp·px，默认 0 | 同上，垂直方向 | 垂直方向也想压时才开。人手本来就能一路下拉，默认关 |
| **水平轴权重** | 0–1，默认 1.0 | 在「标定值」之上再乘一个**使用比例** | 想压得保守一点（更像人、留点残差给自瞄）就调小。见下面「行程 vs 权重」 |
| **垂直轴权重** | 0–1，默认 0.0 | 同上，垂直 | 同上 |
| **录制用 FOV** | 30–120°，默认 80 | 录制时把像素换算成角度用的视场角 | 只在**录制**时有用，而且只要和你录的时候一致就行（补偿比例是 S/Θpp，FOV 会约掉） |
| **左右翻转** | 开 / 关 | 补偿方向取反 | 压完反而飘得更厉害 ⇒ 先拨它，比改代码快 |
| **上下翻转** | 开 / 关 | 同上，垂直 | 同上 |
| **微调垂直轴** | 开 / 关 | 决定下面那张图**画哪条曲线、拖哪条曲线**（关=水平，开=垂直） | 调完水平调垂直时拨一下 |
| **显示开火区域** | 开 / 关 | 画出开火按钮那块矩形（可拖可改大小） | 第一次用必须开：不开就框不到，框不到就永远不触发 |
| **显示标记框** | 开 / 关 | 画出录制时要跟踪的那个小方块（可拖） | 录制前开。同时会画出截图管线中心方块 —— 标记**必须在那个方块里面** |

### 12.2 右栏：档案与竖版弹道图

| 控件 | 说明 |
|---|---|
| **档案** | 下拉选一把枪。存的是**名字**不是序号，所以删掉一个档案不会让已保存的选择指向别的枪 |
| **弹道图（竖版）** | 横轴 = 水平漂移、纵轴 = 时间（第一发在最上）。虚线灰 = 原始测量，实线 = 微调后。**拖第 k 发 = 从第 k 发起之后全部错位**（阶梯语义，§8.3）—— 因为要改的是「第 k 发这一下动了多少」，曲线是这些位移的累积 |
| **恢复** | 清空微调，回到纯测量曲线 |
| **保存** | 把微调写进 `<name>.tune.json`。**原始测量文件只读**，不会被手调盖掉 |

### 12.3 「整梭行程」怎么调（30 秒）

1. 找面墙，站定，打满一梭，**只开水平**（垂直权重先关）。
2. 看弹着点：往**左**散 ⇒ 补偿不够 ⇒ **加大**「整梭行程·水平」；往**右**散 ⇒ 加过头 ⇒ **调小**。
3. 散得最窄的那一档就是这把枪的值。**记下来** —— 同一灵敏度下别的枪可以直接套，因为它是「手指要拖多远」，和枪的角度无关。

反解出的 α（度 / finger px）与平均每发量显示在状态行：**同一个 α 能套所有枪**，这是这个单位的好处。

### 12.4 「行程」和「权重」有什么区别

两个数都在缩放同一个量，容易混。区别在**语义**：

- **整梭行程 S** 是**标定值** —— 它是这把枪的物理属性（在这套灵敏度下）。换枪要重标，标完就不动。
- **权重** 是**使用偏好** —— 1.0 = 原样照压，0.7 = 只压七成。留三成残差有两个用处：更不像机器人，以及给自瞄留一点可修正的量。

### 12.5 三条触点路径（为什么"共用触点"不用管）

压枪**不新增手指**，它给已经在视角区里的那根手指**加位移**。按当时谁拿着那根手指分三种情况：

| 情况 | 谁的手指 | 压枪加在哪 |
|---|---|---|
| 自瞄开着、在驱动 | 自瞄的合成手指 | 直接加进 `st.position`（`aim_section.cpp` 两处：Pressed 与 Holding） |
| 自瞄开着/关着，玩家手在视角区 | 玩家自己那根（镜像） | `reader_set_view_offset()`，偏移跟着镜像走 |
| 只有压枪、没人按着视角区 | 压枪自己按一根 | 自己 `UINPUT_SLOT_PRIMARY`，按在家位置再累加 |

**三种情况都在「自瞄那个触摸区域」里压** —— 所以和自瞄天然共用触点，不需要任何开关去协调。这也是 §4.3 那个「让出水平轴」开关被删掉的底气：两者根本没有互斗。
